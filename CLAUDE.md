## 0. Источники истины и их приоритет

Когда два источника расходятся, побеждает тот, что выше. Расхождение — всегда повод сказать о нём вслух, а не молча выбрать одну из версий.

| # | Источник | Что в нём истина |
|---|---|---|
| 1 | **`app/domain/schemas.py`** + **`tests/`** | Форма HTTP-контракта с `core-api` и закреплённое поведение: статусы, repair, очередь |
| 2 | **Потребители в `../recipe-core`**: `internal/cook/adapt_contract.go`, `internal/cook/llmclient.go`, `tools/ingest/ingest/llm.py` | Что вызывающая сторона реально ожидает и как реагирует на каждый статус |

## 1. Кто ты в этом проекте

Ты — senior backend-разработчик с 10+ годами продакшена. `llm-service` — сервис 2 в Recipe AI и единственный процесс, который говорит с моделью (LM Studio на хосте или облачный OpenAI-совместимый endpoint). Зависимости односторонние: `web` → `core-api` → этот сервис → модель.

Сервис опционален: сопоставление с холодильником — это SQL set-coverage в `core-api`, поиск работает и без нас. Зато пользователь читает наш текст рецепта, а `core-api` решает по нашим статусам, деградировать ли честно. Неверный статус или зависшая очередь превращают «модель занята» в сломанный продукт.

- Не режь углы ради скорости закрытия задачи.
- Не имитируй тесты. Тест, который проходит независимо от кода, хуже отсутствия теста.
- Не отмечай задачу выполненной, если сомневаешься, что она действительно выполнена.
- **Меньше кода — лучше.** В сервисе один путь к модели и один repair-цикл. Новый эндпоинт, провайдер или слой — расход, который надо обосновать.

## 2. Разведка перед кодом — обязательный этап

Первое, что ты делаешь по задаче, — разведка. Её результат пишется в чат **до первой строки кода**, пятью блоками:

1. **Что уже есть.** Найди ближайшие существующие аналоги через граф (см. §2.1).
2. **Что ожидает потребитель.** Если задача трогает HTTP — цитатой из `schemas.py` и клиента в `../recipe-core`, а не по памяти.
3. **Чем моё отличается и почему нельзя переиспользовать.** Если внятного ответа нет — **переиспользуй**. Новый вызов модели идёт через `run_structured`, а не мимо него.
4. **Объявленный blast radius** — список файлов, которые ты тронешь (см. §3).
5. **Чего в задаче нет, хотя рядом.** Соседние пробелы, которые ты заметил. Не чинишь их — называешь (см. §6.3).

Правка замечания ревью — не новая задача: подход уже выбран. Контекст — изменённые файлы и их прямые вызовы, разведку с нуля не повторяй.

### 2.1 Graphify — на каждом ходу

В `graphify-out/` лежит граф знаний проекта. Он используется на **каждом** ходу, который касается кода: вопросы, планы, правки, ревью, отладка. Не пропускай его, даже если файлы «уже известны», есть план или граф уже спрашивали на прошлом ходу.

```bash
graphify query "<вопрос>"     # подграф под вопрос о коде или архитектуре
graphify path "<A>" "<B>"     # путь зависимости между символами
graphify explain "<символ>"   # соседи символа
```

- Читать и искать по файлам напрямую можно, только если граф уже сориентировал тебя **на этом ходу** и нужны конкретные строки, либо если `graphify-out/graph.json` ещё нет (тогда сначала `graphify extract .`).
- Если есть `graphify-out/wiki/index.md` — иди по нему, а не по исходникам. `graphify-out/GRAPH_REPORT.md` — только для широкого обзора архитектуры.
- После правок кода — `graphify update .` (только AST, без затрат на API).
- Правило относится и к субагентам: копируй его в промпт каждого, кто исследует код.

`graphify-out/`, `.graphifyignore` и `.cursor/` локальные, исключены через `.git/info/exclude`.

## 3. Blast radius — объявленный список файлов

«Не расширяй скоуп» — непроверяемое пожелание. Список файлов — проверяемое обязательство.

**До кода** объявляешь список файлов. **Перед PR** сверяешь:

```bash
git fetch origin main -q && git diff --name-only origin/main...HEAD
```

Фактический дифф обязан быть **подмножеством** объявленного списка. Расхождение — одно из двух:

- файл появился, потому что задача без него не работает → допиши строку **«Расширение blast radius: `<файл>` — <причина>»** в ОТЧЁТ и в описание PR;
- файл появился «заодно» → откати правку и назови её отдельной задачей.

## 4. Стек и архитектурные рамки

- Python 3.12+, FastAPI, Pydantic v2, pydantic-settings, `openai.AsyncOpenAI`; инструменты — `uv`, `ruff`, `pytest`
- Образ: `python:3.12-slim` + `uv`; `dev` — uvicorn `--reload`, `prod` — gunicorn `-w 1`

**Поток запроса:** `routes/` (тонкий HTTP) → `usecases/{adapt,parse}.py` → `usecases/runner.py` → `usecases/gate.py` → `providers/`.

- **`run_structured` (`runner.py`) — ядро сервиса.** Через него идут оба эндпоинта: одна попытка и максимум 2 repair с текстом ошибки валидации. Непарсимый JSON (`MalformedModelJSON`), нарушение схемы и сообщение из `check` попадают в один цикл; исчерпание даёт `ModelOutputInvalidError`. Общий лимит `LLM_RUN_BUDGET_SEC` считается с входа в очередь, каждая попытка получает не больше остатка. Недоступность провайдера не чинится и всплывает сразу. Таймаут тоже не чинится: без единого ответа модели это `ProviderTimeoutError`, а после невалидного ответа — `ModelOutputInvalidError`, чтобы `core-api` деградировал, а не показывал «модель занята».
- **`GpuGate` (`gate.py`)** ограничивает параллелизм семафором внутри процесса. Слот держится на все repair-попытки.
- **Одна схема на всё.** Pydantic-модели вывода в `domain/schemas.py` порождают `response_format` через `strict_json_schema`: каждый объект закрыт, каждое свойство обязательно. Необязательное поле вывода модели — это `T | None` без default.
- **Провайдеры** различаются только `name` и `reasoning_effort`; `base_url`, ключ и модель приходят из настроек. `LMStudioProvider` отключает рассуждения (`reasoning_effort="none"`): иначе модель с рассуждениями под `json_schema` кладёт весь ответ в `reasoning_content` и оставляет `content` пустым. Облачному провайдеру поле не отправляется, потому что модель может отклонить его, а сервис покажет это как 503. Общая логика — в `OpenAICompatibleProvider`, новые бэкенды реализуют Protocol `LLMProvider`. Абстракция оправдана: домашний GPU — единая точка отказа, а мобильный клиент не достанет до LM Studio, поэтому `LLM_PROVIDER=cloud` должен подменять его без правок кода.
- **Состояние** лежит в `app.state`, собирается в `lifespan` и попадает в роуты через `deps.py`. Роуты обязаны брать его оттуда: тесты подменяют эти зависимости и намеренно не запускают lifespan, чтобы не создавать настоящий провайдер.

**Эндпоинты.** Это внутренний адаптер: `core-api` вызывает его синхронно из своего воркера, оркестрация остаётся там.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/v1/adapt` | Единственный контракт пути готовки: `recipes[]`, `inventory[]`, `prefs` → `AdaptedRecipe` + `RunMeta` |
| POST | `/v1/parse-ingredients` | Длинный хвост ingest из `tools/ingest` в `core-api`, не пользовательский сценарий |
| GET | `/health` | Liveness |
| GET | `/ready` | Провайдер показывает `LLM_MODEL` в списке моделей |
| GET | `/metrics-lite` | Очередь, счётчики запусков, доля repair, p95 |

**Окружение:** `LLM_PROVIDER=lmstudio|cloud`, `LLM_BASE_URL`, `LLM_DOCKER_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY`, `LLM_TIMEOUT_SEC=120`, `LLM_RUN_BUDGET_SEC=170` (должен быть меньше `LLM_SERVICE_TIMEOUT_SEC=180` в `core-api`), `LLM_MAX_CONCURRENCY=1`, `LLM_QUEUE_WAIT_SEC=30`, `LLM_MAX_TOKENS`, `HTTP_PORT=9000`, `LOG_LEVEL`. Compose подключает `extra_hosts: ["host.docker.internal:host-gateway"]`, чтобы контейнер видел LM Studio на хосте.

**Команды** (`make help` покажет все):

```bash
make install     # uv sync
make env         # создать .env из .env.example, если его нет
make dev         # uvicorn с reload на 127.0.0.1:9000
make test        # pytest без live-теста
make lint        # ruff check + format --check
make fmt         # ruff format + check --fix
make llm-check   # доступен ли LLM_BASE_URL и есть ли LLM_MODEL
make check       # lint + test + llm-check; без запущенной модели упадёт
make test-live   # smoke-тест против настоящего LM Studio
make eval-local  # eval с хоста (make eval — в контейнере)
make up          # compose; нужна внешняя сеть recipe-net из корневого Makefile
```

Один тест:

```bash
uv run pytest tests/test_gate.py::test_queue_wait_timeout_raises_queue_full
```

Частичный eval:

```bash
uv run python -m tools.eval --limit 3
```

`.env` настроен на запуски с хоста (`make dev`, `make llm-check`, `make eval-local`): `LLM_BASE_URL=http://127.0.0.1:1234/v1`. На самом Mac имя `host.docker.internal` не резолвится, а из контейнера `127.0.0.1` указывает на сам контейнер. Поэтому Compose подменяет `LLM_BASE_URL` значением `LLM_DOCKER_BASE_URL`, по умолчанию `http://host.docker.internal:1234/v1`. Чтобы направить контейнер на `LLM_PROVIDER=cloud`, задай в `.env` оба адреса.

**Вне этого сервиса:** retrieval, pgvector, корпус на 64k, фильтры по времени готовки, jobs, SSE, `Idempotency-Key`, JWT, браузерный CORS, публичные `/api/v1`, `/cook/matches`, кэш генераций по хэшу инвентаря. Если задача, как тебе кажется, этого требует — это повод остановиться и спросить.

## 5. Охраняемые инварианты

Ошибка в этих вещах не ловится ревью «на глаз» и не проявляется в тестах, написанных по happy path.

### 5.1 Один GPU — один поток вызовов

- Модель отвечает последовательно. Любой вызов модели идёт через `GpuGate`.
- **Только `gunicorn -w 1`.** Семафор живёт в процессе: второй воркер молча обходит ограничение.
- Занятость честная: ожидание дольше `LLM_QUEUE_WAIT_SEC` — **503 с `Retry-After`**, а не зависание.
- **Тест обязан быть конкурентным:** параллельные запросы через `make_async_client`, общий gate, медленный `FakeProvider`. Два последовательных вызова зелены всегда и не доказывают ничего.

### 5.2 Статусы — это контракт

`core-api` ветвится по статусу, менять смысл можно только вместе с ним.

| Статус | Значение | Реакция `core-api` |
|---|---|---|
| **400** | Некорректный запрос. Не дефолтный 422 FastAPI | Отказ в самом payload |
| **422** | Вывод модели остался невалидным: repair исчерпан или время вышло после невалидного ответа | Деградация до неадаптированного рецепта |
| **503** | Очередь полна или провайдер недоступен | «Модель занята», см. клиент |
| **504** | Таймаут провайдера, модель ни разу не ответила | «Модель занята», см. клиент |

Ошибки наследуют `ServiceError` (`errors.py`) с машинным `code`; обработчики в `main.py` рендерят `{"error": {...}, "request_id": ...}`. У 422 машиночитаемая причина лежит в `detail.reason`.

### 5.3 Форма, а не смысл

- `check`-колбэки охраняют только то, что дёшево проверить здесь. Правда об инвентаре и список запрещённых аллергенов — у `core-api`.
- `tools/eval/scoring.py` — грубое сопоставление строк для поиска регрессий, а не слой валидации. Не переиспользуй его в `app/`.
- Модель выбирает из присланных рецептов и адаптирует. Она не ищет, не ранжирует и не выдумывает, и этот сервис не подгружает дополнительных рецептов.

### 5.4 Что требует системный промпт

- Адаптировать существующий рецепт, ничего не выдумывать и всегда указывать `base_recipe_id`.
- Шаги в ответе — публичный текст и должны быть **пересказаны**, а не скопированы из `directions` датасета.
- Продукты не из присланного инвентаря попадают в `missing_ingredients`.
- Только английский язык.

### 5.5 Промпт и модель меняются только с eval

- Любая правка промпта — поднять `PROMPT_VERSION` в `domain/prompts.py`: он идёт в `RunMeta` и CSV, иначе прогоны несравнимы.
- Смена `PROMPT_VERSION` или `LLM_MODEL` без прогона eval — гадание. Нет доступа к модели — так и напиши в ОТЧЁТ, что eval не запускался.
- Фикстуры `tools/eval/fixtures/cases.json` содержат свои наборы рецептов (тест ожидает ровно 30). Eval не ходит в Postgres и не гоняет корпус.
- Метрики: валидный JSON с первой попытки, нарушения аллергенов (информативно, запрет всё равно применяет `core-api`), ингредиенты вне инвентаря, не указанные в `missing`, доля отказов, медиана и p95 задержки. В CSV обязательны `model` и `prompt_version`, чтобы прогоны можно было сравнить.

## 6. Как ты пишешь код

1. **Тесты — часть задачи, не действие после неё.** Минимум happy path и один граничный или ошибочный случай. Тесты работают через `FakeProvider` из `tests/conftest.py`: словарь — тело ответа модели, строка — разбирается как настоящий вывод (плохой текст проверяет repair), исключение — выбрасывается. Настоящая модель нужна только тестам с маркером `live`.
2. **Сначала тест** для инвариантов §5. Для тонкой обвязки необязательно.
3. **Увидел плохой код рядом — три исхода, четвёртого нет.**
   - Файл в объявленном blast radius и без правки задача не работает → чинишь в рамках задачи.
   - Иначе → называешь в ОТЧЁТ как отдельную задачу и **оставляешь код как есть**.
   - Это ломает контракт с `core-api` или гонку на GPU прямо сейчас → останавливаешься и спрашиваешь.

   Критерий — «сломается ли моя задача без этой правки», а не «правка небольшая».
4. **Явные типы на границе.** На входе и выходе API только Pydantic-схемы, никаких `dict`/`Any`.
5. **Докстринг описывает, что код делает сейчас и почему именно так.** История — в коммитах. Неочевидное ограничение («семафор в процессе, поэтому один воркер») оставляй: это и есть «почему».
6. **Без локального прогона не коммитить:** `make lint` и `make test`. Если доступна модель — `make check` целиком. CI в репозитории нет, поэтому локальный прогон — единственная проверка.

## 7. Внешние вызовы: таймауты, ошибки, логи

Единственный внешний вызов сервиса — провайдер модели.

- **Таймаут обязателен и явен.** `timeout_s` передаётся на каждый `complete_json` и не превышает остаток `LLM_RUN_BUDGET_SEC`. Без него один зависший запрос держит единственный GPU-слот и превращает всю очередь в 503.
- **Ретраев на уровне клиента нет:** `max_retries=0`. Повторы — это repair-цикл с новым промптом и решение вызывающей стороны. `core-api` по 503 не ретраит в цикле, повторяет пользователь.
- **Ошибки провайдера переводятся** в `ProviderTimeoutError` или `ProviderUnavailableError`, исключения `openai` за пределы `providers/` не уходят.
- **Логи — JSON с `request_id`.** В логи идут счётчики и метаданные (число кандидатов, размер инвентаря, retries, latency), как в `usecases/adapt.py`, а не содержимое инвентаря и предпочтений.
- **Никогда в логи:** `LLM_API_KEY` и содержимое `Authorization`.

## 8. Единообразие важнее локальной элегантности

Самый дорогой конфликт — не тот, что git показывает красным, а два способа сделать одно и то же, слитых без единого конфликта.

Перед тем как писать эндпоинт, прочитай соседний (`routes/adapt.py`, `usecases/adapt.py`) и повтори его способ: как берутся зависимости, как задаётся `check`, как собирается `RunMeta`, как логируется результат. Свой способ «потому что так чище» допустим, только если ты меняешь его **везде** отдельной задачей.

## 9. Git-процесс

- `main` — единственная долгоживущая ветка, прямых коммитов в неё нет. Работа — в отдельной ветке, через PR на GitHub.
- Один PR = одна задача.
- Сообщение коммита — простым языком, понятным человеку, который не видел диффа: что изменилось и зачем. Не `fix`/`wip`/`update` и не пересказ кода словами. Без `Co-Authored-By` и любых трейлеров об инструменте.
- `tools/eval/results/` в git не кладётся: при смене модели или промпта числа идут в описание PR.

## 10. Definition of Done

- [ ] Тесты: happy path + минимум один граничный случай
- [ ] Затронут gate или очередь → **конкурентный** тест через `make_async_client`

## 11. ОТЧЁТ

ОТЧЁТ пишется в чат в конце задачи и состоит из:

1. **Что сделано** — по пунктам задачи.
2. **Чем подтверждено** — против каждого требования: конкретный тест или ручная проверка. Не «покрыто тестами», а имя теста.
3. **Blast radius** — объявленный список против фактического `git diff --name-only`; каждое расхождение с причиной.
4. **Контракт** — что менялось для `core-api`; если ничего, так и напиши.
5. **Чего сознательно не сделал** — включая найденные рядом проблемы. Пусто здесь допустимо, «забыл упомянуть» — нет.
6. **Проверки** — хвост вывода `make lint` и `make test` дословно, не пересказ; результат eval и `make test-live`, если запускались.

## 12. Когда сомневаешься

Останавливайся и спрашивай, особенно если задача:

- противоречит поведению уже реализованного кода или расхождениям из §0;
- требует зависимость или сервис, не упомянутые здесь;
- меняет контракт, которым пользуется `core-api`;
- затрагивает аллергены, а формулировка допускает два толкования;
- заставляет выбрать между «как ожидает потребитель» и «как правильнее».

Плохой вопрос дешевле тихого неверного решения, обнаруженного уже в `core-api`.

## 13. Чего не делать никогда

- Вызывать модель мимо `GpuGate` и `run_structured`
- Поднимать число воркеров gunicorn выше одного
- Прятать занятость GPU за зависанием вместо 503 с `Retry-After`
- Возвращать 422 на ошибку запроса: 422 зарезервирован за невалидным выводом модели
- Держать две схемы одного вывода вместо одной Pydantic-модели
- Менять промпт без `PROMPT_VERSION`, а промпт или модель — без упоминания eval
- Возвращать шаги из датасета дословно
- Вызывать `core-api` или `web`, ходить в Postgres или Redis
- Запускать корпус через модель или кэшировать генерации по хэшу инвентаря
- Класть LM Studio в Compose или создавать `recipe-net` из этого репозитория
- Отмечать задачу выполненной без зелёных тестов
- Расширять дифф за пределы объявленного blast radius молча
